# 装好之后怎么验

> 一次完整的验收清单：A 段工具行、B 段轮末改动卡、C 段会话装配。每条都是「做什么 → 期望看到什么」，
> 不过的时候看最后的「没过怎么定位」。插件的行为口径以 [`../README.md`](../README.md) 为准。

## 前提

1. **生效方式分两半**：客户端半身（`lib/client.js`）每次页面加载都从磁盘取——刷新窗口就够；**host 半身
   （`lib/index.js`）只在 harness 进程启动时装载**，而 DSH Desktop 关窗口只是缩到托盘、进程不退。动过 host
   半身必须让 harness **真的重启**；只刷新窗口的症状是「客户端文案变了、host 路由却始终不存在」（POST 落到
   静态前端拿 405）。这一条曾经把我们拖了四轮，所以写在最前面。
2. 排错先读日志：`<DSH_HOME>/logs/host/dsh-<日期>.log`（同目录还有 `.error.log`）。host 半身挂载成功会写
   `[dsh-edit-diff] host half loaded` 与 `reveal route mounted at /edit-diff/reveal`；**两行都没有 = host
   半身压根没装载**，别去改业务代码。
3. 静态门禁（每次改完都要回到这里）：

   ```bash
   npm test          # = node test/smoke.mjs && node test/host.mjs
   ```

   客户端半身**不需要重启 harness**：`lib/client.js` 每次页面加载都从磁盘取，改完刷新窗口即可。

语法着色与背景高亮那一块（A7-A15）另有一层离线验证：`test/smoke.mjs` 直接对**插件自带的本地分词器**
（`__internals.highlightDiffLines`）断言，覆盖「未知语言 = 纯文本、已知语言逐行给出 runs、关键字/字符串/
注释/数字/调用名各归各类、颜色只取主题的 `--shiki-token-*` 变量、转义引号不提前闭合、多行三引号与模板串
跨行成一段、单个引号不跨行、星平面字符不把 token 边界算错、无彩色 token 的行仍然返回自己的 runs」，
回退任一条即失败。

**散文不是代码**（2026-09-21 用户截图反馈「着色怎么这么奇怪」后补的，四条断言各自对应一个真缺陷）：
markdown 整个不做分词（`PLAIN_LANGS`）；`yaml`/`toml`/`ini` 只做词法着色、单词不分类（`lexicalOnly`）；
单字符引号只在前面不是单词字符时才开串（`shiki's` 不再吞掉整行）；SCREAMING_CASE 要长度 > 1
（单个 `A` 不再被染成常量色）。这四条**只有把真实卡片渲染出来看才能发现**——
分词器单测当时全绿，因为它测的是「每个 token 分对了类」，而缺陷是「这个类根本不该分」。

**教训：桩替代真实依赖的地方，必须另外核对依赖的真实导出面。** 早先的桩提供了
`highlightLines` / `subscribeGrammarLoaded` / `grammarLoadCount` 三个函数，而 shipped 的
`@deepseek-ai/dsh-client-ui-primitives@0.1.5-rc.2` **只定义、不导出**这三个（`export {}` 里没有）。
插件解构它们 → 三个都是 `undefined` → 一开卡就崩；后来改成读命名空间 + `typeof` 守卫 → 不崩了，
但守卫拿到 `undefined`，于是**静默降级成纯文本，一个颜色也没有**，而 `npm test` 全程全绿。
桩是「按调用方期望的形状」写的，不是「按模块真实导出表」写的，所以它验证的是插件怎么用，不是插件用得上。
**该桩已删除**：现在分词器是插件自己的，不再有任何非导出依赖可被假桩掩盖。
核对一行即可：`grep '^export {' <primitives>/lib/index.js`。

**像素级验收口径**（本轮实际做过，harness 不入库）：用一次性脚本加载 `lib/client.js`，
以真实主题样式表（`ui-theme` 的 `base.css` + `shiki.css`）+ 插件自身 CSS，把 `EditDiffRow`
的真实 DOM 渲染成静态页，再用 headless Edge 截图，暗/亮两套主题各一张。结论：`.py` 的关键字/
字符串/跨行 docstring/注释/数字各归其色、整行底色铺满、改动处底色加深；`.md` 为纯文本 + 底色。
**这一步不能省**——上面的四条缺陷全是它发现的。A17/A18 也是这一步抓出来的：`/* … */` 的第二行
在截图里明显是关键字色、里面的反引号还被染成字符串，而当时的分词器单测全绿。

**轮末卡的诊断口径**（2026-09-21 用户反馈「轮末的小卡片怎么没有了」）：把会话日志
（`~/.dsh/sessions/<workspace>/<session>/session.v3.jsonl.zstd`，**多帧 zstd**，Node 的
`zstdDecompressSync` 只解第一帧，要按 magic 切帧逐帧解）里的**真实事件**回放进
`turnChangesDefinition()`，即可离线判定累积器与 `select` 是否成立。当时的结果是
「turn 1 = 45 条、turn 2 = 7 条、turn 3 = 0 条」，证明累积器与 `seq <= owner.seq` 过滤都没问题，
问题只可能出在**接线**（槽位/累积器有没有注册上）。同一份日志还确认了真实 `tool/call` 的
`data.arguments` 是字符串、`tool/result` 带 `surfaceOp: "append"` 与 `data.meta.diffs`。
**`select` 抛异常会被渲染器当成「拒绝」**（`chain selector crashed … treating as declined`），
所以 `select` 现在绝不抛；而「拿不到 `uiConversation` 就整段 return」的旧写法会同时掐掉槽位与累积器，
测试里还把它当成预期行为钉住了（断言「只注册四个工具行」），现在改成断言**五个**（四个工具行 + 轮末槽）。

**链式槽的选举 ≠ keyed 槽的去重**（2026-09-21 的真因：卡片整晚没出现过，而且「数据对、select 命中、
组件能渲染」全都成立）：`conversation.chat.turnTail` 是 **chain** 槽——同一 priority 允许有多个注册者，
链按 priority 升序试，第一个非 null 的赢，**同优先级按注册先后**（`entriesOfSlot` 对 chain 原样返回
那个稳定排序的数组）。第三方插件 `dsh-better-sidebar` 0.19.1 也在同一个 `-1` 上注册同一条链，它的
`select` 只要「这一轮有产物文件」就认领——正好是本卡要接管的那批轮次——于是谁先被 loader 挂载谁赢。
屏幕上唯一的症状是「本卡不见了，轮末换成一排文件名 chip」，和「这一轮没改文件」几乎分不出。
本插件因此把轮末条目降到 `-100`（严格低于遮蔽内置行用的 `-1`），并在注册后订阅该槽，
**一旦出现不高于本插件优先级的邻居就 `console.warn` 点名**。
反过来，keyed 槽（`tool.call.toolview`）同 key 同 priority 会被注册表当场拒绝（"already has an entry
for key …"），撞了会报错，不会静默——**能静默输掉的只有 chain**。

## 没过怎么定位

按嫌疑排序，每一步尽量只改一处、只验一条：

1. **完全没反应**（工具行也还是 DSH 内置样式）→ 先确认客户端有没有加载到插件：
   `dsh --profile <profile> --dump-config | grep -A2 "id: edit-diff"`；
   `cd $DSH_HOME/profiles/<profile> && node -e "console.log(require.resolve('dsh-edit-diff/client'))"`。
   两者都对，就基本是「没重启」。
2. **A 全过、B 完全不出卡** → **先排除链上被别人截胡**：看 Console 有没有
   `[dsh-edit-diff] 轮末链上有不高于本插件的占用者：…` 那句（有 = 邻居优先级 ≤ `-100`，本卡必输），
   并留意轮末是不是**别人的卡**（一排文件名 chip / 别的样式，而不是内置「本次产出」）——那说明槽位、
   累积器、`select`、组件全都正常，输的是**选举**。chain 槽同优先级按注册先后，改加载顺序赢不了，
   只能降自己的 priority（见上面「链式槽的选举 ≠ keyed 槽的去重」）。
   排除之后，再分清「没接管」还是「没数据」：把 `lib/client.js` 里的
   `selectChangedFiles` 临时改成无条件 `return { changed: [] }`，重启看是否出现空卡。
   出空卡 = 接管没问题、是累积器没攒到数据；仍不出卡 = 注册/让位环节有问题。
   注册与定义的写法可对照 `@deepseek-ai/dsh-client-ui-deliverables/lib/client.js`
   （`producedForClosing` / `selectDeliverables` / 它那个 definition），它用同一套契约。
   累积器攒到数据却从不接管，先查**入账条目的 seq**：`selectChangedFiles` 按
   `entry.seq <= owner.seq` 过滤，而框架给 definition 的 `match` 对象是
   `{ event, role, location }`，**没有 `seq`** —— 写成 `appendChanged(state, match.seq, ...)`
   会让每条 entry 的 seq 都是 `undefined`，比较恒为 false，卡一次都不出现（2026-09-19 修过，
   见 `test/smoke.mjs` 里按「先 match 再 update」驱动的累积器用例）。
3. **B6 漏 PTC** → dispatch 记录的路由没走通：确认 `tool/ptc-dispatch-start` 的 `parentCallId`
   能回溯到 `run_code` 的根 `callId`，而那个根 `tool/call` 必须已先被同一个 definition 见过。
   真实字段读法在shipped 的 `@deepseek-ai/dsh-client-ui-chat/lib/client.js` 的 `childCall` / `childResult` 里核对。
   **B7 只在向上翻页时漏** → 路由表记晚了：`prepend` 先 match 整页、再统一 update，
   路由表必须在 `match` 阶段学习（本插件在 `rememberCallRoute()` 里做）。
4. **视觉/颜色不对** → token 名用错：对照
   `@deepseek-ai/dsh-client-ui-primitives/lib/DiffBlock.module.css`。
5. **打开历史会话整片空白、只剩「加载更早」** → 装配在 `flush()` 里断了（C1 的失败形态）。
   DevTools Console 里找 `Cannot read properties of null`。最常见的是 definition 的
   `buildLocationData` 首帧拿到 `previous === null` —— 框架 `emptyLocationData()` 的初值是
   `{ step: null, turn: null }`，**不是 undefined**，写成 `previous !== void 0` 就会放行 null。
   核对方式：直接 `definition.buildLocationData({ state }, "turn", null)`，能过才安全；
   单测里也要用 `null` 而不是 `void 0`，否则正好绕过这个分支。
   `previous` 是本 definition 上一帧发布的数据，但它可能来自**旧版本/热重载前**的同一个 key，
   所以 `previous.value?.changed === changed` 这种读法要能容下 `value` 为空，别让一句属性访问
   掀翻整个 `flush()`。

改完必须回到「前提」第 3 步的静态门禁，并在 `dsh-edit-diff/` 下开一个只含本次改动的提交。

## 已闭合：行内区间曾经是碎片（2026-09-22）

**症状**（2026-09-21 用户截图反馈「怎么高亮又出错了」）：行内「再深一档」的区间是碎片，不是一块。
与「整行底色」这条既定设计无关——整行底色是 A2 要求的。用插件自己的管线（`__internals.hunkRows`）
跑真实的一对改动行（本仓提交 `9a6c36d` 的 diff），当时得到的 `marks` 是：

```
- [74,79)「regis」 [81,84)「ati」 [85,86)「n」
+ [36,47)「.slice(0, 4」 [48,49)「)」 [87,91)「ool 」 [93,94)「w」
```

被替换的整词只被标出几个互不相邻的碎片，连单独的 `n`、`w` 都各自成片。

**根因**：`charMarks()` 把**逐码点 Myers 的未对齐下标**直接当区间。Myers 会把 `registrations` 与
`tool rows` 之间能对齐的公共字符（`o` / `r` / `t` 一类）算作「没变」，剩下的未对齐字符天然不连续。
**区间没算错，错的是「未对齐码点」这个定义不是读者要的语义**——读者要的是「这一行里哪一段被替换掉了」。

**改法**：对齐粒度从码点换成**单元**。`markUnits()` 把一行切成「词 / 空白 / 单个 CJK 字符或标点」
（CJK 刻意不并进词规则：整句一个词会让改一个字就高亮整句），对这些单元跑 Myers——直接复用数组泛型的
`myersChangedLines`（它只比 `===` 和 `.length`，本来就与「行」无关）——再由 `rangesOf()` 把未对齐单元
换算回**码点**下标（`markedText` 的切片空间，所以代理对不会被劈开）。相邻单元、以及**只隔空白**的两个
改动单元并成一块。顺带：单元的编辑距离恒 ≤ 码点的编辑距离，所以过 `MAX_EDIT_DISTANCE` 退回的情况只少不多。

**验收证据**（实际跑过，非推断）：

- `test/smoke.mjs` 里那对**真实行**已成 fixture，断言落在**区间本身**：`del [[74,87]]`（一块，
  覆盖 `registrations`）、`add [[36,47],[48,49],[86,96]]`（三处真实改动各一块，第三块覆盖 `tool rows `）；
- 粒度护栏：CJK 改一字只标那一字（`[[9,10]]`）、跨空格的两词替换并成一块（`[[2,12]]`）；
- 原有断言全部保持：`[[7,15]]`、`[[6,7]]`、星平面整颗 emoji；
- 渲染层：真实卡片跑两遍（`smoke.mjs` 有语法 run / `notes.md` 无），原文**各出现恰好一次**、
  被替换的词整块标记。`notes.md` 是 4 个 span 精确对应 4 个区间；`smoke.mjs` 是 10 个 span——
  那是 `markedText` 按 token 边界切开同一个区间，拼接结果一致，**不是碎片**（碎片是标记之间夹着
  未标记的文字）。

**为什么断言必须落在区间上**：`markText` helper 把 mark span 拼起来，而碎片拼起来正好等于完整的词，
所以这个缺陷当时逃过了全绿的 `npm test`。**助手按调用方期望的形状写，就会掩盖真实缺陷**——与前面
「primitives 只定义不导出高亮器」那条是同一类教训。

**未做**：像素级（headless 浏览器 + 真实主题样式表）那一步本轮没跑，做的是同一张真实卡片在
JSON DOM 层的核对；A20 的 live 观感仍待在真卡片上看一眼。

## 已闭合：碎片回来了，换成「孤立汉字」的形态（2026-09-22）

**症状**（用户截图反馈「你的着色好像又出错了」）：词级对齐之后，改动区间**又**碎了——但这次碎片
更大、更容易误判成「着色错了」。真实的一对行（README 的那段）：

```
del 标记: 「这个号可能不是文件里的真行号」。区分 | 靠字形而 | 是靠颜色 | 本来就有 | ，
```

**根因**：CJK 是**逐字**分词的（为了「改一个字只标一个字」的精度），于是常见汉字（不、就、的、出）
在两侧**偶然**匹配，把被替换的短语从中间切开——`不是` → `不要` 里的那个 `不` 被当成了共享字符。

**这不是着色问题**：着色管文字颜色，行内加深管哪一段被标记，两层无关。换高亮器（shiki）对这个
缺陷毫无帮助。

**改法**：只碰标记这一层，两条规则。

1. `gapJoins()`——两个改动之间的空档**全是非词字符**（空白 / 标点 / 符号）时并成一块。
   - 反引号与空格不承载意义，`` `~` 前缀 `` → `` `?` 后缀 `` 必须是一块，而不是 `~` + 空档 + `前缀`。
   - 空档里只要有**一个词字符**就是有意义的边界：`alpha, beta` 的逗号被吞掉，而 `x = 1; y = 2;`
     里的 `y` 与 `=` 挡住合并，`1` 和 `2` 各自成块。
   - 空白空档本来就在这条规则里，多词替换 `tool` + `rows` → `tool rows` 一并保住。
2. `MARK_COVERAGE_MAX = 0.8`——一行被标记的**比例超过 80%** 时两侧都不标。这条是**合并规则的直接
   后果**：如果两侧只剩标点还共享，那些标点匹配会被规则 1 全部吞掉，整行变成一块（用户截图反馈
   「全被加深了」）。标记不再有区分力时，行底色已经说了「这行变了」。阈值是量出来的：合法的两词
   替换覆盖 **71-73%**，重写段落覆盖 **85-97%**，线画在 80%。两侧一起丢，半标的一对读起来像 bug。

**试过并撤掉的规则**（**不要再加回来**）：把**夹在改动中间**的孤立单汉字匹配当作巧合丢掉。
它确实能让 `靠字形而不是靠颜色` → `不要` 不再从中间切开，但同一规则也会把 `前缀`/`后缀` 之间
**真正共享**的 `缀` 丢掉，于是整个 `前缀` 被染深——过度标记。实测下来只留上面两条，
两种症状**都**解决了，而且代码更少（撤掉 `matchedPairs()` / `isSingleCjk()` /
`dropCoincidentalMatches()` 三个函数）。**教训：先量「加上这条规则后所有用例的输出」，再决定它是否必要。**

**验收证据**：真实行对给出 `靠字形而不是靠颜色` **一整块**；`` `~` 前缀 `` 一块（`[[3,7]]`）；
`alpha, beta` 一块（`[[2,13]]`）而 `x = 1; y = 2;` → `x = 3; y = 4;` 保持两块（`[[4,5],[11,12]]`）；
重写段落**完全不标**（真实段落实测 86% / 91%）；`甲不乙`/`甲要乙` 与 `中文测试`/`中文测式`
两条护栏钉住精度边界；真实行 fixture 增侧为 `[[36,49],[86,96]]`；`npm test` 全绿。

## 本轮完成（2026-09-22，三项待做 + 一项未决全部收口）

### 1. 不等长 run 配对（已实施）

改动前的 `withMarks()` 只在**删增行数相等**时配对，而且**按位置**配对——两半都错：增侧多一行
就整块不加深；在 run 顶部插一行会让后面每一对错位，加深落到别的行上。

改法：`pairRun()` 做**顺序保持的最大相似度对齐**（零空档罚分的 Needleman-Wunsch），相似度是
**字符级 Dice**。删增行数不等不再需要特例——多出来的行没有对应者，保持素行即可。相似度必须
**严格大于 0** 才成对（两行一个字符都不共享时，标满两侧本来就会被覆盖率规则丢掉）。run 超过
`MARK_PAIR_CELLS = 16384`（128×128）时返回 null，**等长**的退回按位置配对（改动前的形状），
不等长的完全不标——两条都只是退化成旧行为。

**为什么相似度用字符而不是 `markUnits` 单元**：必须认出来的正是「换了词的同一行」，而
`registrations` → `tool rows` 的单元交集是**空**的，按单元算会把主 fixture 判成不相干、标记全丢。
实测该 fixture 的字符级 Dice > 0.8。

**为什么没采用「把两侧 token 流拍平后一起 diff」**：那条路同样能修不等长，但它把「配对」这个概念
消掉了，而覆盖率规则（一行标满就不标）是按**一对**行表述的；按行配对能原样复用已经调好的
`charMarks()`，全部既有断言一字不动地继续成立。

**验收证据**（实际跑过）：

- 新增断言：run 顶部插一行 + 删 1 增 2 的 fixture，删侧 `[[14,19]]`（`count`）、
  与之配对的增侧行 `[[14,19]]`（`tally`）、插进来的那行 `[]`；
- `pairRun` 契约：等长逐行配对、顶部插入不抢配对、顺序保持下留出未配对、空边不配对、
  无共享字符不配对、超上限返回 null；
- `lineSimilarity`：相同行 = 1、无共享字符 = 0、空行 = 0、一字符共享 = 0.5、
  主 fixture > 0.8；
- **回退即失败（实测）**：把改动前的 `lib/client.js` 放进临时目录、配**新的**测试跑，
  失败信息正是 `an unequal run still marks the removed side, got: []`；
- 全部既有标记断言（`[[74,87]]`、`[[36,49],[86,96]]`、CJK 精度、`gapJoins` 三条护栏、
  重写段落不标）保持原样通过——`charMarks()` 本身未改，改的只是谁跟谁配。

### 2. 私有 crash boundary（已实施）

两个槽位的组件都经 `guarded()` 包一层插件自己的 `CardBoundary`（React 类组件）。抛异常时
**保住这一行**：显示「差异卡渲染失败」+「重试」，并 `console.error` 点名卡片与错误。重试给子树
换一个 key 重挂，而不是复用抛过异常的树。React 只把 render / lifecycle 的异常送到 boundary。

**验收证据**：`guarded()` 正常路径直通、不出现 fallback；抛异常的子树产出 fallback
（含 message / retry / 行容器 `dsh-edit-diff-root`，**异常没有逃出去**）；诊断同时点名卡片与错误；
点重试后 `failed=false`、`attempt=1`，再渲染即回到子树；样式表断言 retry 是 pill。
测试桩为此升级：`expand()` 现在按 React 的方式实例化**类组件**（原来当普通函数调用会抛
"Class constructor … cannot be invoked without 'new'"），并把 `render` 的异常交给
`getDerivedStateFromError` 重画一次——否则 boundary 根本没法验。

### 3. context boost（已实施）

参数推导出来的 hunk 是**裸片段**，展开就是凭空两行。`/edit-diff/read` 本来就要为行号读这个文件，
同一次读现在把片段**前后各 3 行**（`CONTEXT_LINES`）一起带回来。那几行是文件自己的行，所以
行号列显示**真实行号**；按 hunk 的同一份 `indent` 一起去缩进（否则 hunk 贴左、上下文还缩进着）；
与 hunk 的行一起送进分词器，跨行字符串的状态是连着的。

**只给参数推导的 hunk**（`source: "args"`）：metadata hunk 自带 `structuredPatch` 的 3 行上下文，
再补一份就是 6 行。**只给新侧有锚**的片段：那些行要按锚换算行号，没有锚就只能退回相对编号。

**验收证据**：`locateBases` 的上下文（每侧 ≤3 行、文件边界截断、纯删除不带上下文、定位不到
返回空上下文）；`contextOf` 的去缩进；`bodyRows` 的行序列 `["path","ctx","ctx","ctx","del","add","ctx"]`、
上下文行号 `[2,3,4]` 与 `6`、`lineReal` 全真；**每条行的着色 run 拼起来必须等于它自己的文本**
（偏移算错就会取到邻行的 token）；metadata hunk 与未定位片段都不加上下文。
**变异测试**：把 `row.index + offset` 改回 `row.index`，上面那条不变量立刻失败并打印出
`del` 行拿到了 `def run():` 的 token——证明这条断言不是摆设。

`bodyRows(model, bases)` 是从 `DiffBody` 里提出来的**纯函数**：gutter fallback 是异步的，基准迟到
就要重跑一次，提出来才能在**没有 React、没有宿主**的情况下验上下文行与它们造成的着色偏移。
这同时补掉了上一轮记录的「`DiffBody` 的异步接线测试桩覆盖不到」里**行表那一半**。
